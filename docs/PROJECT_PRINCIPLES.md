# プロジェクトの設計原則

この文書は長期間維持する判断基準の正本です。現在の実装構造は [ARCHITECTURE.md](ARCHITECTURE.md)、重要な判断の理由は [ADR](adr/README.md)、コードの記述規則は [CODE_STYLE.md](CODE_STYLE.md)、作業手順は [AGENTS.md](../AGENTS.md) を参照してください。

## 開発の目的と学習方針

- この個人ゲーム開発はSpace Invaders一作で終わらせず、複数の作品を通じてゲーム開発の経験と技術的な判断力を蓄積することを目指します。本リポジトリはその第1弾です。
- Space Invadersの再現とともに、UnityのGameObject・Component・Prefab・Physics2D・Inspector等の特性や制約を実践的に学びます。Unityで学んだ考え方を、将来のUnity・Unreal Engine等での開発にも生かします。
- エンジンの機能を使うこと自体を目的化しません。独自実装にも、制御の明確さ・テスト容易性などの利点があります。仕様への適合、理解しやすさ、保守性、学習効果を比較して選びます。
- 将来使い回すための共通基盤を先回りして作るのではなく、**次の作品でも応用できる知識・設計判断を身につけること**を重視します。

## 再現の目的と根拠

- 第1弾はSpace Invadersのゲームプレイ再現を目的とし、オリジナル要素の追加を優先しません。
- 第1弾は**1P専用**とし、**2P交代プレイとクレジット投入・管理は再現対象外**とします。ゲーム開始・リトライの具体的な操作は別途設計します。
- 原作仕様と、Unityで動かすための実装都合を分けます。開発用の近道や暫定値を原作仕様として扱いません。
- 参考プレイ動画などの根拠に基づいて仕様を確認します。不明な原作仕様を推測で確定せず、参考動画が未指定なら確認します。
- 検証済みの事実・暫定仕様・未確認事項を区別して記録します。論理検証と実際の描画・操作確認も区別します。

## ゲームルールとエンジン機能

- ゲーム固有の移動・攻撃・得点・Wave進行等のルールは、その責務を持つオブジェクトやクラスへ置きます。必ずUnity非依存のC#へ集約することも、すべてをMonoBehaviourへ集約することも求めません。
- GameObject・Transform・Collider2D・Physics2D・Prefab等の採用を積極的に検討します。ただし、再現したい挙動に対して独自の論理処理が適する場合は、その選択を妨げません。
- 位置・生死・弾の状態などについて、何が正となる情報源かを明確にし、Transformと独立モデル等による**同一状態の二重管理**を避けます。原作に合わせた論理ピクセルの扱いとUnity上の座標・表示倍率の関係も明示します。
- 描画FPSの差でゲーム速度や判定結果が不適切に変化しないようにします。Update・FixedUpdate・Physics2D・独自の論理tickは、必要な精度と挙動に応じて使い分けます。特定の更新方式や60Hzを全作品の必須条件にはしません。
- 性能については推測だけで優劣を決めず、必要に応じてProfiler等で計測します。

## 責務分担と相互作用

- 個体の生死・被弾など個体固有の処理は、その個体または明確に指定された担当に置きます。集団の移動・生存数・発射元の選択などは、集団を管理する担当に置きます。
- ゲーム全体の進行やState遷移の担当が、個体の座標計算や当たり判定の詳細まで抱え込まないようにします。
- オブジェクト間の連携には、用途が明確な操作メソッドや通知を使います。UnityのComponent同士が必要な参照を保持することは認めますが、参照先の内部状態を自由に操作できる設計にはしません。
- 当たり判定の検出方法（Physics2Dや独自判定）と、命中後に誰が被弾・撃破・得点・全滅処理を担当するかは分けて検討します。

## カプセル化と依存方向

### 自然に使えるAPIと初期化

- Prefab等で必須設定を構成したComponentは、通常操作だけで使えるAPIにします。利用者に隠れたInitialize→有効化→発射や、内部の回収手順を要求しません。呼出順が不可欠なら、その理由と担当を明記します。
- 必須参照・設定の準備は責任と時点を一つに決めます。Prefab保存時の参照設定やAwake等を選び、保険として発射・状態変更・描画から繰り返し初期化しません。非アクティブGameObjectではAwakeが遅延することも踏まえ、保証できる構造へ変えます。
- 下位Componentは全体管理者を保持・検索・初期化引数で受け取らず、発生した事実をevent/delegateで通知します。所有・管理側が購読と解除を担当し、通知先がなくても個体の通常操作は完結します。具体的な命中対象への操作と、管理者への結果通知は区別します。
- 利用元固有の制約は利用元へ置きます。例えば同時1発はPlayerの射撃制約であり、弾にPlayer専用・管理者必須・他インスタンスとの排他を持ち込みません。
- 状態の正、通知順、Pause/Resume、被弾・得点・Waveの既存意図を維持します。例外が必要なら理由を記録し、汎用Manager・EventBus・不要なInterfaceで解決しません。

Issue #83ではPlayerShotとその接続箇所だけへ適用します。Playerの入力・被弾通知、Formation等の既存依存の整理は別途判断し、この原則を理由に一括改修しません。

### 内部状態の所有

- クラスが所有する可変の管理オブジェクト・ゲームモデルの実体を、公開Getter・property・メソッド戻り値で外部へ横流ししません。読み取り専用のGetterでも、返された参照先の不変性を保証しません。
- 呼び出し側が他クラスの内部オブジェクトをGetterで辿って、さらに状態取得・操作する連鎖アクセスを禁止します。必要な操作は責務を持つ所有者に依頼します。
- 表示をロジックと分離する場合は、不変の値をPushする構造を採用できます。一方、個々のGameObject・Componentが自ら表示を反映する構造も選択肢とします。表示用の状態を複数箇所で不必要に保持しません。
- Editor検証の都合だけでランタイム向け公開APIを増やしません。検証用の読み取り・操作は必要最小限に絞り、`Editor/`配下の専用コードや`#if UNITY_EDITOR`等で製品ビルドから分離します。`UNITY_EDITOR`はEditorのPlay Modeでも有効なため、通常のランタイム処理から検証用APIへ依存しない設計を守ります。
- 単純な値型・enumの読み取りpropertyまで一律に禁止するものではありません。公開APIの妥当性は責務・参照の漏出・依存方向に照らして判断します。

**本節は現在のDriver→表示ControllerへのPush実装を直ちに変更する指示ではありません。** 現行の責務境界や公開APIの具体的な制約は [ARCHITECTURE.md](ARCHITECTURE.md)・[CODE_STYLE.md](CODE_STYLE.md) と既存ADRに従います。方式を変更する際はコード・文書・ADRの整合性を同じ変更で確保します。

## 必要最小限の設計と共有

- Space Invaders固有のゲームルールは専用に実装します。一方、オブジェクトの責務・エンジン機能の選択は、ほかのゲームにも通じる設計の学習機会として扱います。将来用途だけを理由に汎用フレームワークや抽象化を追加しません。
- ChatやNotionは検討・議論に使い、確定した原則・現在構造・重要判断はリポジトリで版管理します。特定のAI製品や過去会話がなくても参照できる状態を保ちます。
- 元ゲームから抽出した画像・音声・動画など、著作権上問題のある素材をリポジトリへ追加しません。
